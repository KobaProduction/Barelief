# Ритмический анализ: офлайн-рецепты

Требования, текущий этап, проверки и handoff разработки ведутся в
[workspace issue #28](https://github.com/ArthurKoba/ai-science/issues/28).
Эта страница описывает реализованный тракт; актуальный исследовательский план
нужно читать в issue.

Интерактивный каталог теперь содержит только `basic-signal` — генератор,
Window и линейный график. Описанные ниже спектральные и ритмические схемы
сохранены через `numeric_fixture_examples()` для офлайн-проверок и не доступны
как пресеты меню. Прежний fixture `startup` сохраняет спектральный тракт и
базовый RhythmAnalyzer; общие входные builders переиспользуются.

| ID примера | Направление | Основные графики |
| --- | --- | --- |
| `rhythm-research` | Базовый 96-полосный Analyzer | История признаков, метрики и BPM |
| `rhythm-fourier-short` | Fourier, 512 кадров | #1206 |
| `rhythm-fourier-long` | Fourier, 4096 кадров | #1216 |
| `rhythm-acf-short` | ACF, 512 кадров | #1209 |
| `rhythm-acf-long` | ACF, 4096 кадров | #1219 |
| `rhythm-tempo-evidence` | Два масштаба Fourier и ACF | Кандидаты #1221, count/maturity/ambiguity #1222 |
| `rhythm-onset-strength` | Log-Mel onset strength | #1305 и Mel-история #1306 |
| `rhythm-onset-max-filter` | Log-Mel, lag2/max-size3 | #1361 и Mel-история #1306 |
| `rhythm-spectral-flux` | Spectral flux | #1322 |
| `rhythm-complex-difference` | Комплексная спектральная разность | #1332 |
| `rhythm-phase-deviation` | Phase deviation | #1342 |
| `rhythm-high-frequency-content` | High frequency content | #1352 |

Только TempoEvidence требует обе длины истории и обе разновидности периодичности
как явные входы своего прежнего алгоритма. Остальные восемь существующих
примеров, включая `music-research` и `temporal-fft`, сохраняют свои рецепты.
При60 кадрах/с полные512/4096 кадров соответствуют8,53/68,27с наблюдения.
Это отдельно от public maturity TempoEvidence: по умолчанию минимальное
наблюдение4с, зрелое8с. Нулевые дополненные строки таблицы не объявляются
кандидатами без соответствующего count. Частота обработки, темп анализа и
GUI FPS — разные показатели; разделение рецептов само по себе не измеряет FPS.

Прежний калиброванный fixture использует **Loopback**. Его аудиотракт:
SpeexDSP (32768 Гц) → окно Hann (4096) → RealFourier → AmplitudePhase →
ArrayMultiply (линейная амплитудная коррекция).

В **ArrayFill #1005** уже включены 2048 измеренных линейных коэффициентов
из сохранённого проекта пользователя (профиль: 32768 Гц, FFT 4096,
Hann, SpeexDSP). При формировании примера исходный пользовательский
config.json не изменялся. Множители применяются до анализа признаков.
Штатный AudioLineView #1110 отображает кривую коэффициентов по частоте,
а график спектра #10 — скорректированные амплитуды.

Спектральные признаки формируются из обычных, уже существовавших узлов:
**BroadbandRow #6**: 24 низкочастотных, 8 среднечастотных и
16 высокочастотных полос (48);
**NoteSpectrum #1006**: 48 нот, MIDI 36–83.
**ArrayConcat #1007** формирует строго 96 частотных/нотных признаков.
**Spectrogram #7** сохраняет исходные 512 кадров ×96 полос Float32.
Эту же историю получают просмотр #8 и Analyzer #1102. Квантования и
восстановления UInt8 в аналитическом тракте нет. History сохраняет значения
выше единицы; только вход Analyzer явно ограничивает их единицей и учитывает
clipped_frames/clipped_values/maximum_before_clamp. Значения0…1, включая слабые
уровни, не меняются; отрицательные и неконечные значения отвергаются.
Выбор хранения для MCU относится к последующему профилю переноса.

Каждая схема переиспользует builder селектора #200 и подключает только нужный
тракт. Калиброванный тракт #332/#2/#3/#4 использует32768 Гц и FFT4096.
Явная кадровая частота перед окном задана только в офлайн-стенде
`numeric_rhythm_replay_graph()` (описан ниже). Остальные калиброванные fixtures
сохраняют rolling Window: публикация следует поступлению пакетов;
объявленная частота схемы сама по себе не ограничивает её60 кадрами/с.

Отдельные reference-onset fixtures используют PcmResampler #1313 (44100 Гц) →
Window #1314 (2048) → периодическое Hann #1310 → ArrayMultiply #1311 → RFFT #1312.
Их rolling Window также публикует результат на каждый пакет. Только офлайн-replay
заменяет #1314 на FrameBuffer2048 с постоянным `hop_samples=512`: первая полная
STFT-рамка начинается с отсчёта0 и выходит после2048 реальных отсчётов,
последующие начинаются с512,1024… Частота этой отдельной ветви44100/512≈86,13
кадра/с не зависит от частоты калиброванного анализа/GUI. Это причинный
`center=false` frontend. Данное правило полных окон не распространяется
на остальные rolling Window fixtures. Исходные методы с иными FFT/hop/centering
требуют своих явных настроек, а не автоматически считаются эквивалентными.
Re/Im эталонной ветви до пользовательской коррекции поступают в:
**SpectrumProjection #1300** (`normalize=false`, линейная raw power) → **Mel #1301** (128 Slaney-полос,
area normalization, явные Fs44100/bin44100÷2048Hz/first_bin0) → **Spectrogram #1302**
(до512 линейных Float32-кадров, `filled_only=true`) → **PowerToDb #1303** → **OnsetStrength #1304**
(center=false, n_fft2048, hop_length512) → **VectorLineView #1305**. Просмотр #1306 показывает линейную
Mel-историю. Эта ветвь наблюдает интенсивность атак; отдельного трекера долей
после неё пока нет. Полная цепочка от записанного post-SRC PCM до признаков
проверяется `tools/rhythm/librosa_pcm_parity.py` против закреплённого librosa1.0.0.
Это не проверка численного соответствия самого ресэмплера.

Комплексный RFFT (`[bin][Re,Im]`, включая DC и Nyquist) используется четырьмя
отдельными пресетами, каждый с одним блоком: **SpectralFlux #1320**, **ComplexSpectralDifference
#1330**, **PhaseDeviation #1340**, **HighFrequencyContent #1350**. Следующие за
каждым NumberAccumulator и VectorLineView сохраняют только реальные значения.
Все сигналы и вычисления — Float32; выходы не ограничены диапазоном 0…1.
Flux суммирует положительные либо абсолютные разности амплитуд; комплексный
метод — расстояния от прогноза с предыдущей амплитудой и фазой
`2φ[n−1]−φ[n−2]`. Half-wave у комплексного метода явно подавляет убывающие
амплитуды. PhaseDeviation усредняет абсолютную обёрнутую вторую разность фазы
по всем переданным bins, с явным амплитудным порогом и опциональным весом.
Это математический mean-вариант, без гистограммной обработки Aubio.
В отдельном max-filter пресете **OnsetStrength #1360** использует log-Mel историю с `lag=2`,
`max_size=3`, `center=false`; #1361 показывает отдельную огибающую с max-фильтром.
Это наблюдаемый вариант подавления спектральных сдвигов, проверяемый через
`librosa.onset.onset_strength(S=…,lag=2,max_size=3)`. Он сохраняет общую
геометрию2048/512/Mel128 и не объявляется точным воспроизведением всей
конфигурации SuperFlux из статьи (иная спектральная сетка/FFT/hop).
HFC суммирует `(k+1)*magnitude[k]`, опционально квадрат амплитуды.
Переносимое ядро: [spectral_descriptors.h](../../libs/dsp_kernels/include/dsp_kernels/spectral_descriptors.h).
Комплексная формула соответствует [Duxbury et al., DAFx03, eq.8–11](https://www.dafx.de/paper-archive/2003/pdfs/dafx81.pdf);
код реализован самостоятельно, GPL-исходники библиотек не включены.
Истории начинаются с нулей и сбрасываются при discontinuity; первые значения
могут содержать переходный процесс. Пики/доли эти блоки не подтверждают.

Переносимое ядро DP-трекера доступно отдельно через
[PreparedBeatTracker](../../libs/dsp_kernels/include/dsp_kernels/beat_tracker.h):
огибающая атак и явный BPM (одно значение или кривая длины истории) → локальная
оценка → накопленная DP-оценка/backlinks → маска долей с trimming. Все рабочие
вычисления Float32, память готовится до вызова; диагностика доступна без копирования.
Это пересчитываемая оценка всего окна, не поток подтверждённых событий: будущий
контекст способен менять прошлые доли. Приём одной рамки/тишины не создаёт долей.
Округлённый период ограничен явным maximum_period_frames и должен быть не менее2;
вырожденный исходный случай с self-link отвергается. Общий GUI/runtime-узел после
OnsetStrength пока не подключён. Проверка
`tools/rhythm/librosa_beat_parity.py` сравнивает исходный метод и Float32-реализацию;
равные в пределах округления DP-оценки могут дать разные пути. Это проверка
математики, отдельно от качества распознавания по человеческой разметке.

В офлайн-replay калиброванная ветвь при60 кадрах/с чередует шаг546/547;
у отдельной эталонной ветви шаг512 постоянен. Ветки сравниваются по исходному
времени; номера кадров и512-строчные истории имеют разную длительность.

По умолчанию офлайн-стенд задаёт ритмическому анализу60 кадров/с.
Стандартный ScalarMetricsView #1103 показывает
текущие ритмические величины; **NumberAccumulator #1105** сохраняет
историю кандидата BPM, **VectorLineView #1106** отображает эту историю
на шкале времени. Runtime готовит геометрию детектора из объявленного
контракта входа: 64 либо 96 линейных значений Float32. Межкадровые положительные
изменения обрабатывает переносимый [PreparedOnsets](../../libs/dsp_kernels/include/dsp_kernels/onsets.h).
Он выделяет причинные пики с адаптивным порогом и исходным временем;
подтверждение пика требует последующего снижения. Его сила — нормированный
контраст, а не вероятность музыкальной доли.

Отдельный диагностический узел `RhythmFeatures` принимает явно выбранный
`input_representation=complex` (RFFT4096, 2049×2 Re/Im) либо `peak_amplitude`
(2048 положительных амплитуд, без DC). Он выдаёт64/96 Float32 полос:
сумма квадратов через общий численный projection, корень и прежний масштаб R4,
с ограничением0…1. Округления до256 уровней в этом пути нет. Формат входа
проверяется против настройки, а не выбирается по длине массива.
Это отдельная проекция; стандартный составной ряд #1007 проходит напрямую.

Положительный спектральный flux (выход7 #1102) поступает в выбранную отдельным
пресетом цепочку. Общие builders сохраняют прежние операции:
**Spectrogram #1200 / #1210** (512 /4096 scalar-кадров) → MatrixTranspose →
MatrixCenter (вычитание среднего) → включённый MatrixWindowFunction (Hann) →
**MatrixFFT #1204 / #1214** → MatrixRow → VectorLineView. Используется
существующая общая FFT, вычисления остаются частью PreparedGraph. При60 кадрах/с
полные истории охватывают8,53 /68,27с, шаг частотной сетки равен0,1171875 /
0,0146484375Гц (7,03125 /0,87890625BPM). Графики показывают частоты модуляции
в герцах; умножение на60 даёт темп периодичности, но гармоники и кратные темпы
ещё не разрешаются в подтверждённую метрическую сетку.

До заполнения история содержит старые нули; реальное число кадров выдаётся
отдельным выходом1 накопителя. Более мелкая FFT-сетка сама по себе не означает
такую же точность оценки при коротком наблюдении. В выбранном пресете
вычисляется только его цепочка; у TempoEvidence нужны оба масштаба.
Обновление с меньшей частотой и MCU-бюджеты ещё не приняты.

В отдельных ACF-пресетах от `MatrixCenter` отходит **MatrixAutocorrelation #1207 /
#1217** → MatrixRow → VectorLineView. Общий переносимый kernel вычисляет
линейную ACF, без циклического FFT-переноса и без повторного накопления внутри
Analyzer. Максимальная задержка120кадров и Fr60 заданы в настройках узла.
Графики показывают signed коэффициент−1…1 по задержке в секундах; темп
периодичности равен60/lag_seconds при положительной задержке. Fourier и ACF
пока являются диагностическими выходами; подтверждение темпа/сетки использует
прежний трекер и этим добавлением не объявляется исправленным.

Встроенный спектральный observer выдаёт события с неизвестным типом:
позиция полосы в составном массиве не задаёт Bass/Snare/Clap/Hat.
Разные спектральные диапазоны не становятся независимыми свидетельствами
метрического уровня. Ядро позволяет явно задать несколько диапазонов через
`rhythm::Config::onset_channels`; штатный runtime сейчас анализирует один
полный ряд. Подтверждённые атаки диапазонов перед IOI объединяет причинная
fusion с исходными временами и маской каналов. Её ожидание включает
незавершённые пики; один ряд дополнительного окна ожидания не получает.
Подробные поканальные наблюдения доступны в kernel Output;
12 числовых выходов runtime ещё не передают этот набор и журнал событий.

Исследовательский Python oracle остаётся проверкой неизменённой typed-event
машины. Новый spectral observer проверяется отдельными временными,
геометрическими и allocation регрессиями. Неопределённая сетка остаётся
неопределённой до достаточных музыкальных свидетельств.

Дополнительные истории широкополосного и нотного рядов (#1008 и #1010)
остаются доступны для отдельных спектрограмм. Пользовательский файл
проекта не изменяется; обновлённый пример нужно открыть явно.

Коэффициенты усиления могут быть больше единицы и не конвертируются в dB.
Mel остаётся линейным; логарифм мощности вычисляет только явная ветвь атак.

Для воспроизводимых измерений WAV через этот же frontend доступен
[офлайн-стенд rhythm_replay](../../apps/rhythm_replay/). Его явный
`numeric_rhythm_replay_graph()` содержит обе periodicity-ветви и все шесть
reference-огибающих. Эта fixture не входит в интерактивный каталог и не
подключается скрыто через startup. Стенд сохраняет полный/сокращённый Float32,
поканальные наблюдения и штатные статусы анализатора; разметка читается только
отдельным evaluator. Реализация подачи WAV и часов находится в
[replay.cpp](../../apps/rhythm_replay/src/replay.cpp), композиция — в
[numeric_rhythm_graph.cpp](../../apps/default_graphs/src/numeric_rhythm_graph.cpp).

Только в этом replay калиброванный маршрут проходит через
PcmResampler #332 → одновходовый Mixer #333 (`ClockedFifo`, вес1) → Window #2
(4096). Отдельный SampleClock #334 явно задаёт32768 Гц; прежние часы #16
и генератор #1 сохраняются. Частота анализа `Fr` выбирается CLI:30,45 или60 Гц.
Существующий `SampleCadence` задаёт рациональные шаги выходного PCM:
при Fr60 средний шаг32768/60=8192/15, то есть546/547 отсчётов, а не постоянный546.
FFT и анализ запускаются после выдачи очередного PCM-интервала перед Window;
удержание спектра после FFT не используется для формирования этой частоты.

Для кадра k стенд ждёт одновременно фактический входной конец не раньше
`ceil(k*Fsin/Fr)` и достаточное число реальных отсчётов в FIFO после ресэмплера.
Номинальный выходной конец `floor(k*32768/Fr)` сам по себе не разрешает тик.
Часы обслуживаются последовательно после завершения подачи входного пакета,
без повторного входа в исполнитель из callback. Ёмкость FIFO и выходной
контракт проверяются при подготовке; потеря отсчётов, underrun и неверное
число потреблённых отсчётов отвергаются. Дедлайн кадра, готовность данных
текущего пакета и задержка SRC — разные величины.

Window #2 сохраняет прежний startup с нулями слева: первый кадр не ждёт
полного4096-отсчётного окна. Это отличается от полной первой рамки2048/512
эталонной ветви. На EOF стенд не добавляет будущих тиков, нулевого хвоста
или flush ресэмплера. Неполный период остаётся в FIFO; если физический дедлайн
уже наступил, но реальных PCM для него недостаточно, replay возвращает ошибку.
Эти правила относятся к offline replay; остальные rolling Window fixtures
не получают такую кадровую частоту автоматически.

`reference_envelopes.csv` отдельно сохраняет шесть raw Float32-огибающих
эталонной44100Гц ветви. Для каждого значения есть начало, центр и конец
STFT-окна в исходных отсчётах/секундах, готовность текущего пакета и nominal SRC
latency. Эти величины не смешиваются с60Гц кадрами калиброванной ветви.
Опция CLI `--reference-trace` дополнительно выгружает Float32 LE:
`reference_pcm.f32` (выход штатного SRC), `reference_fft.f32` (Re/Im),
`reference_power.f32`, `reference_mel.f32`, `reference_db.f32` (последняя строка
текущей истории). Размеры и параметры записаны в `summary.json/reference`.
Стенд объявляет ёмкость PCM-пакета как у источника, так и на селекторе;
пакеты больше256 не обходят проверку совместимости.

[librosa_pcm_parity.py](../../tools/rhythm/librosa_pcm_parity.py) сравнивает
этот фактический PCM→STFT→Mel→dB→onset путь с закреплённой librosa1.0.0.
Для dB/onset используется только доступный prefix истории (до512 кадров):
будущий максимум всего файла не подменяет причинный `top_db`.
Математика четырёх комплексных descriptor-вариантов проверяется на записанных
Re/Im отдельно, чтобы фаза численного шума разных FFT backend не выдавала
ложное расхождение метода. SRC-фильтр этим сравнением не проверяется.

### Эталонные схемы в локальном GUI

Явная настройка CMake `BARELIEF_RHYTHM_REFERENCE_GUI=ON` добавляет в меню
пресетов раздел «Эталонные алгоритмы ритма». В нём четыре потоковые схемы:
Aubio, BTrack, madmom CRF и Essentia MultiFeature. Они применяются через тот же
исполнитель графов, что и остальные пресеты. Графики отдельных выходов открываются
из узлов схемы. Другие варианты и полновходные WAV-режимы доступны через
