# Уроки работы с агентами

Эти правила появились из повторяющихся ошибок при изменении runtime, редактора
и визуализации. Они помогают сохранить смысл задачи при параллельной работе.

## Проверять пользовательский путь

Готовая схема и тест отдельного API не проверяют, что пользователь может создать
узлы, соединить их, изменить параметры, применить и сохранить проект. Приёмка
должна воспроизводить исходное действие пользователя. Для дефекта сначала
зафиксируйте наблюдаемый результат и ожидаемое поведение в issue.

## Разделять результаты и доказательства

Сборка подтверждает компиляцию. Авторский тест проверяет свой сценарий.
Независимый review проверяет границы и ошибочные случаи. Offscreen не доказывает
нативную отрисовку или работу физического устройства. У итогового результата
должны быть указаны редакция, сценарий и границы проверки.

## Сохранять поздние решения владельца

Исторические stereo-обязанности, фиксированный темп и прежние команды нельзя
возвращать из старого плана после изменения требований. Перед работой сверяйте
архитектуру, текущее issue и последние решения владельца. Новое направление
уточняется у владельца, а принятое поведение отражается в документации после реализации.

## Не исправлять данные оформлением

Перестановка подписей осей не исправляет порядок матрицы. Индекс полосы не
становится герцами без координат, а индекс кадра — секундами без времени.
Исправляйте контракт и преобразование данных на ответственной границе.

## Не подменять исполнение визуализацией

GUI отображает результат обработки. Закрытие графика не должно останавливать
схему; диагностический preview не меняет параметры DSP. Ускорение одного графика
не подтверждает производительность полного приложения с несколькими представлениями.

## Декомпозировать работу по ответственности

У каждого параллельного исполнителя есть свои файлы и завершённый результат.
Общий API согласуется с владельцем напрямую. Один координатор управляет общей
сборкой. Постоянные микрогейты и повторные поручения мешают автономному завершению
блока и создают конкурирующие версии статуса.

## Сохранять только устойчивую документацию

Отчёт проверки и рабочий план принадлежат issue. В архитектуру переносится
устройство принятого решения, в историю — существенная веха, в эту страницу —
повторяющийся урок. Такой перенос не означает копирование всей переписки.
