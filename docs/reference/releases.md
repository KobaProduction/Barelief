# Версии и GitHub Releases

Git — единственный источник версии. `scripts/git_version.py` используется
всеми CMake-профилями и CI через `cmake/GitVersion.cmake`. Ручного файла версии,
счётчика запусков CI и зависимости версии от времени сборки нет.

Ближайший тег `vMAJOR.MINOR.PATCH` на first-parent истории задаёт базу.
Каждый следующий first-parent коммит прибавляет единицу к patch; merge считается
одним коммитом этой линии. Например, четыре коммита после `v1.2.3` дают `1.2.7`.
Повторные сборки не меняют версию. Major/minor меняются отдельным решением
владельца через новый стабильный тег. База Barelief `v1.0.0` соответствует
коммиту `0caec43`, где появилась исходная версия продукта.

Нужны полная история и version tags, в том числе этот начальный тег на origin.
CI использует `fetch-depth: 0`; неполный checkout или отсутствие базы отвергаются
явно. Рабочие деревья и packed refs поддерживаются. CMake отслеживает Git refs,
индекс и исходники: следующий обычный build обновляет identity после коммита,
тега или изменения файлов без обязательного ручного configure.

Числовая версия одинакова в приложении, SDK, Windows VERSIONINFO и CPack.
`build-identity.json` дополнительно содержит полный commit SHA и `build`:
`g<SHA>` либо `g<SHA>.dirty.<хеш содержимого>`. Стадирование не меняет эту
identity; изменение байтов меняет. Незакоммиченная сборка получает суффикс
`-dirty-<12 hex>` в именах пакетов. Игнорируемые build/package outputs не влияют
на identity. Manifest устанавливается в `bin` и копируется в
`<имя-пакета>.identity.json` для каждого CPack-архива или установщика.

Обычные ветки и PR проходят быстрый CI. Ветка `release` предназначена для
явного продвижения уже проверенного коммита с сохранением его SHA, без
добавочного merge-коммита. `Release validation` запускает полный Windows,
Linux и portable набор, затем упаковку. Только после успеха всех jobs стадия
`publish` проверяет чистоту источника, SHA, версию и build identity каждого
Windows ZIP/EXE и Linux DEB. Она формирует SHA256SUMS и публикует GitHub Release,
создавая вычисленный `vMAJOR.MINOR.PATCH` на том же исходном коммите.

Ручной `Release validation` по умолчанию только проверяет и собирает пакеты;
параметр `publish` явно включает публикацию. Существующий тег не переносится,
релиз и его assets не перезаписываются при повторном запуске. Dirty-пакеты,
разные SHA/версии, неполный комплект платформ или неизвестный manifest
блокируют публикацию. Код разрешения версий и подготовки публикации сам
не выполняет сетевых записей.

Кнопка проверки обновлений в приложении использует опубликованные стабильные
GitHub Releases. Наличие нового коммита, тега или CI artifact само по себе
не означает, что пользователям уже доступно обновление.
